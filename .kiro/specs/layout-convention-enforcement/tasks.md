- [ ] 2. レイアウト解析: ID 集合の収集とスナップショット取得
- [ ] 2.1 レイアウト索引を拡張して ID 集合と除外コンテナ出現数を収集する
  - 既存の address→id 走査と同一トラバーサル(二重走査なし)で、除外コンテナ配下を除く全ウィジェット ID 集合を収集する
  - 除外コンテナ id 自体は ID 集合に含め、除外コンテナ id ごとの出現回数を別途カウントする
  - 重複アドレス警告など既存の warnings 生成は不変に保つ
  - 完了条件: unit テストで「除外配下の除外」「コンテナ id 自体の包含」「重複出現カウント」「既存警告の維持」が緑になる
  - _Requirements: 1.1, 4.2, 4.3_

- [ ] 2.2 レイアウトスナップショットストアを新設する(読み込み + 検証 + last-good)
  - refresh / current を持つストアとして、レイアウトファイル読み込み(throw と undefined/非オブジェクトの両方を失敗扱い)・索引構築・警告収集を一括提供する
  - dynamic コンテナ出現数はコンテナ型(panel / modal / tab / root)のみ計数し、非コンテナ型に id `dynamic` が付いている場合は計数せず「欠落」として警告を記録する(validate-design Issue 2 の決定)
  - dynamic コンテナが 2 つ以上のときは重複警告を記録し、適用は継続できる状態を返す
  - root 直下ウィジェット配列を注入 edit の土台として抽出し、セッション形式外なら空配列 + 警告とする
  - 失敗時は直近の正常スナップショット(last-good、1 世代)を返し続け、一度も成功していなければ null を返す
  - 完了条件: unit テストで「初回失敗 → null」「成功 → 失敗 → last-good 維持」「コンテナ型判定と重複カウント」「root 配列欠如時の空配列 + 警告」が緑になる
  - _Requirements: 3.1, 3.3, 4.2, 4.3, 6.1, 6.2, 6.3, 6.4_

- [ ] 3. 適用計画: 生成 ID の一意化とコンテナ注入
- [ ] 3.1 生成ウィジェット ID をレイアウト既存 ID と決定的に一意化する
  - 適用計画の構築入力をスナップショットへ切り替え、used-set をレイアウト全 ID + 予約 id(root / dynamic)で初期化する
  - 衝突時はサフィックス(`_2`, `_3`, … の最小空き番号)で一意化し、グループパネルと見出しの生成 ID も同一 used-set を通す
  - 乱数・時刻を使わず、同一のマニフェスト + スナップショットから常に同一の計画を生成する
  - ID 変更はウィジェット id のみに作用し、address・値同期・Unity 通信内容は不変に保つ(手動ウィジェット側は常に無変更で生成側が譲る)
  - ID 衝突の発生を自己修復イベント(id-collision)として計画に含める
  - 完了条件: unit テストで「決定性(同一入力 2 回で deepEqual)」「正規化衝突(`/a/b` と `/a_b`)」「手動 ID との衝突サフィックス」「グループ/見出し ID の一意性」「衝突なし時の出力が旧実装と一致(回帰)」が緑になる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 2.3, 5.1_

- [ ] 3.2 dynamic コンテナ欠落時の注入 edit を計画に組み込む
  - コンテナ出現数 0 かつ dynamic エントリ 1 件以上のときのみ、root 直下ウィジェット配列 + 注入モーダルの全置換 edit を edits の先頭に置く(既存 root 子を必ず含める)
  - 注入モーダルは設計の決定値(modal 型 / id `dynamic` / 右下小ボタン + ポップアップ / widgets 空)で生成し、中身は後続の dynamic コンテナ edit が投入する
  - コンテナ存在時は注入せず既存コンテナを受け皿にし、欠落 + エントリ 0 件では注入もコンテナ edit も発行しない
  - edits の順序(注入 → 既存ウィジェット → dynamic コンテナ)と valueSyncs 後置を計画内で保証し、注入発動を自己修復イベント(container-injected)として計画に含める
  - 既存の計画構築警告(range 非対応など)は従来どおり警告として出力し続ける
  - 完了条件: unit テストで「注入 3 パターン(存在 / 欠落+0 件 / 欠落+1 件以上)」「edits 順序の保証」「注入 edit に既存 root 子が含まれること」が緑になる
  - _Requirements: 3.1, 3.2, 3.3, 5.1, 5.2_

- [ ] 5. ランタイム統合: 適用経路の配線と旧規約の撤廃
- [ ] 5.1 起動時検証から旧規約を撤廃しスナップショットストアへ移行する
  - 旧レイアウト規約検証(予約プレフィックス禁止・dynamic コンテナ必須)のモジュールとそのテストを削除し、起動時に呼び出さない
  - 起動時はスナップショットストアの refresh を best-effort 実行し、レイアウト読み込み失敗でもランタイムを起動継続する(config 失敗時の停止は従来どおり)
  - 完了条件: unit テストで「`dyn` プレフィックス ID を含むレイアウトで警告が出ないこと」「レイアウト読み込み失敗でも起動継続」が緑になり、廃止モジュールへの参照が残らない
  - _Requirements: 2.1, 2.2, 4.1, 6.4_

- [ ] 5.2 マニフェスト適用直前の再読み込みとイベント仲介を配線する
  - マニフェスト受理後・計画構築前に必ずスナップショットを refresh し、レイアウトの編集・保存内容を再起動なしで次回適用に反映する
  - refresh 失敗時は layout-reload-failed を記録して last-good で適用を継続し、last-good も無い場合は適用をスキップしてマニフェスト再要求に戻す(ping・値同期・受理済み適用の配信は影響を受けない)
  - 計画の自己修復イベントを detail 文字列へ整形してイベントログに仲介する(イベントログは適用経路を import しない依存方向を維持)
  - スナップショット警告は直前スナップショットとの差分のみログし、警告発生時も適用を継続する
  - /sys/* と /surface/* のフィルタ分岐は無変更に保ち、vendor へは既存グローバル(loadJSON・receive・settings・app)経由のみでアクセスする(O-S-C 無改造で完結)
  - 完了条件: unit テストで「適用直前 refresh の呼び出し」「失敗 → last-good 適用 + イベント記録」「last-good なし → スキップ + 再要求」「警告の差分ログ」が緑になる
  - _Requirements: 3.5, 4.4, 5.2, 5.3, 6.1, 6.2, 6.4_

- [ ] 5.3 sessionOpened で注入を含む適用結果を安全に再現する
  - 受理済みマニフェストを計画と併せて保持し、計画が注入 edit を含む場合のみ refresh + 計画再構築を行ってから新規クライアントへ適用する(レイアウト修復後に古い root 構成を配信しない。validate-design Issue 1 の決定)
  - 再構築時の refresh 失敗は保持中の計画をそのまま適用して継続する(last-good 方針と同一)
  - 注入 edit を含まない計画は再構築せず従来どおり適用し、正常系のコストを増やさない
  - 完了条件: unit テストで「注入発動中の sessionOpened で refresh + 再構築が行われること」「レイアウト修復後は古い root 構成を配信しないこと」「非注入計画は再構築されないこと」が緑になる
  - _Requirements: 3.4, 6.2_
