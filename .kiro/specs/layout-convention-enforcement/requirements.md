# Requirements Document

## Project Description (Input)
レイアウト規約の構造的強制。現在 custom module はレイアウト規約違反(dynamic コンテナ欠落、手動ウィジェットの dyn プレフィックス使用)を起動時に警告ログで通知するだけで、人間が気を付けて守る運用になっている。これを構造的に不可能にする。(1) dyn プレフィックス予約規約の撤廃: buildApplyPlan が生成ウィジェット ID を layout index の既存 ID と照合し、衝突時はサフィックス付与で一意化する。手動ウィジェットはどんな ID でも安全になり、予約プレフィックス規約と関連する警告・検証を廃止する。(2) dynamic コンテナの自己修復: マニフェスト適用時に dynamic コンテナがレイアウトに存在しない場合、custom module が root への /EDIT でコンテナを注入して生成ウィジェットの受け皿を復活させる。O-S-C 本体は無改造のまま custom module 内で完結させる。既存の layout-convention 検証・テスト(layout-convention.ts / layout-convention.test.ts)は新しい責務分担に合わせて再編する。

## Introduction
本仕様は、O-S-C custom module が課しているレイアウト規約 2 件(「id `dynamic` のコンテナ必須」「手動ウィジェット ID の `dyn` プレフィックス使用禁止」)を、警告ログによる人間依存の運用から、custom module 自身が構造的に違反を無害化する仕組みへ置き換えるものである。生成ウィジェット ID はレイアウト既存 ID との衝突時に自動で一意化され、dynamic コンテナは欠落時にマニフェスト適用の過程で自動注入される。これによりレイアウト作成者は規約を意識せずに任意の ID・構成でレイアウトを編集できるようになる。

## Boundary Context
- **In scope**: custom module(`packages/custom-module`)内のマニフェスト適用計画の構築、生成ウィジェット ID の一意化、dynamic コンテナの自動注入、レイアウト規約検証の責務再編とそれに伴う警告の廃止・変更、マニフェスト適用直前のレイアウトファイル再読み込み (see D-2, D-4)
- **Out of scope**: O-S-C 本体(`vendor/open-stage-control`)の改造、Unity 側実装および `/sys/*` プロトコル(`docs/UNITY_PROTOCOL.md`)の変更、マニフェストスキーマ(`packages/shared`)の変更、既存レイアウト JSON 資産(`layouts/`)の書き換え
- **Adjacent expectations**: 既存のマニフェスト駆動 UI(Phase 2)・診断パネル(Phase 3)・誤接続ガード(Phase 5)の挙動は本変更後も維持されること。E2E テスト(`tests/`)は新しい挙動に追従して更新されること

## Requirements

### Requirement 1: 生成ウィジェット ID の自動一意化
**Objective:** レイアウト作成者として、手動ウィジェットにどんな ID を付けてもマニフェスト由来の生成ウィジェットと衝突しないでほしい。ID 命名規則を暗記して守る必要をなくすためである。

#### Acceptance Criteria
1. When マニフェスト適用計画を構築するとき, the custom module shall 生成ウィジェットに割り当てる各 ID をレイアウトに存在する既存ウィジェット ID の集合と照合する
2. If 生成ウィジェット ID がレイアウト既存 ID と衝突する場合, the custom module shall サフィックス付与により衝突しない一意な ID をその生成ウィジェットに割り当てる
3. The custom module shall 同一のマニフェストと同一のレイアウトの組み合わせに対して、常に同一の ID 割り当て結果を生成する
4. The custom module shall 生成ウィジェット同士(グループパネルおよびその見出しウィジェットを含む)の間でも ID を重複させない
5. While 生成ウィジェット ID が一意化により変更された状態, the custom module shall 当該ウィジェットの OSC アドレス・値同期・Unity との通信内容を ID 変更前と同一に保つ

### Requirement 2: dyn プレフィックス予約規約の撤廃
**Objective:** レイアウト作成者として、`dyn` で始まる ID を手動ウィジェットに自由に使いたい。予約プレフィックスという暗黙の規約と、その違反警告に煩わされないためである。

#### Acceptance Criteria
1. The custom module shall 手動ウィジェットの ID に対して予約プレフィックスに関する制約を一切課さない
2. When 起動時にレイアウトを検証するとき, the custom module shall `dyn` プレフィックスを使用した手動ウィジェット ID を規約違反として警告しない
3. When `dyn` で始まる ID の手動ウィジェットを含むレイアウトに対してマニフェストを適用するとき, the custom module shall 当該手動ウィジェットの定義と値を破壊せずに適用を完了する

### Requirement 3: dynamic コンテナの自己修復
**Objective:** レイアウト作成者として、dynamic コンテナをレイアウトから削除・リネームしてしまっても生成ウィジェットが表示されてほしい。コンテナ欠落という規約違反を silent な機能喪失にしないためである。

#### Acceptance Criteria
1. When マニフェストを適用する際に id `dynamic` のコンテナがレイアウトに存在しない場合, the custom module shall O-S-C の編集機構(/EDIT)を通じて root 直下にモーダル型の dynamic コンテナ(開閉ボタン + ポップアップ)を注入する (see D-1)
2. When dynamic コンテナを注入した後にマニフェスト適用を継続するとき, the custom module shall 生成ウィジェットを注入したコンテナ内に配置して表示可能にする
3. If dynamic コンテナがレイアウトに既に存在する場合, the custom module shall コンテナの注入を行わず既存コンテナをそのまま受け皿として使用する
4. When 新しいクライアントセッションが開いたとき, the custom module shall コンテナ注入を含む受理済みの適用結果を当該クライアントにも再現する
5. The custom module shall dynamic コンテナ注入を含むすべての自己修復動作を O-S-C 本体の改造なしに custom module 内で完結させる

### Requirement 4: レイアウト規約検証の責務再編
**Objective:** 開発者として、レイアウト検証ロジックが新しい責務分担(構造的強制)と整合していてほしい。廃止された規約の検証コードや警告が残って混乱を招かないためである。

#### Acceptance Criteria
1. The custom module shall 廃止された規約(予約プレフィックス禁止、dynamic コンテナ必須)に関する検証および警告ログを出力しない
2. If id `dynamic` のコンテナがレイアウトに複数存在する場合, the custom module shall 警告を記録し最初に検出した 1 つのみを受け皿として扱う
3. When 起動時にレイアウトを読み込むとき, the custom module shall 存続する検証(アドレス重複・インデックス構築時の警告など)を従来どおり実行する
4. When 自己修復(dynamic コンテナ注入、または生成ウィジェット ID の衝突回避)が発動したとき, the custom module shall 発動の事実と対象をサーバーログに記録し、ブラウザの診断表示にも配信する (see D-3)

### Requirement 5: 既存機能の互換性維持
**Objective:** 運用者として、規約強制方式の変更後も既存のレイアウトとマニフェスト駆動 UI が従来どおり動作してほしい。安心して更新を取り込むためである。

#### Acceptance Criteria
1. While dynamic コンテナが最初からレイアウトに存在し ID 衝突もない状態, the custom module shall 従来と同一のマニフェスト適用結果(既存ウィジェットへのプロパティ反映、動的ウィジェット生成、値同期)を生成する
2. When マニフェスト適用計画の構築中に警告が発生したとき, the custom module shall 従来どおり警告をログに記録し適用処理を継続する
3. The custom module shall Unity との `/sys/*` プロトコル(ping-pong、マニフェストハンドシェイク、誤接続ガード)の挙動を本変更の前後で不変に保つ

### Requirement 6: レイアウト照合表の適用直前再読み込み
**Objective:** レイアウト作成者として、レイアウトを編集・保存したら O-S-C サーバーを再起動せずに次のマニフェスト適用へ反映されてほしい。「保存したのに古い照合表で動く」という暗黙の再起動運用をなくすためである。

#### Acceptance Criteria
1. When マニフェスト適用計画を構築するとき, the custom module shall 構築の直前にレイアウトファイルを再読み込みして最新のウィジェット ID・アドレス照合表を構築する (see D-4)
2. If レイアウトファイルの再読み込みに失敗した場合(読み取りエラー・JSON 不正など), the custom module shall 直近に正常読み込みできた照合表を用いてマニフェスト適用を継続し、失敗をサーバーログと診断表示に記録する (see D-5)
3. The custom module shall サーバー起動後にレイアウトファイルが編集・保存された場合でも、サーバー再起動なしに次回のマニフェスト適用へ最新のレイアウト内容を反映する
4. While レイアウトファイルの再読み込みが失敗し続けている状態, the custom module shall 既存機能(ping-pong、値同期、受理済みの適用結果の配信)を停止させない

## Dig Summary

- ラウンド数: 2 / 質問数: 5 / 決定数: 5(D-1〜D-5)
- 主要な発見:
  1. 「保存後は再起動が必要」問題を本 spec に取り込むことになり、Requirement 6 としてスコープが拡大した(D-2)
  2. ID 照合表はマニフェスト適用の瞬間にしか使われないため、「適用直前に毎回再読み込み」でファイル監視なしに常時最新を保証できる(D-4)
  3. コンテナ注入は診断モーダル(diag_modal)と同じモーダルパターンを再利用し、既存レイアウトを隠さない(D-1)
- 全決定は上記「Open Questions and Decisions (Dig)」の表を参照
- 残リスク(設計フェーズへ持ち越し):
  - 注入モーダルの具体的な配置座標・サイズ、および既存ウィジェットとの重なりの最終確認
  - 自己修復イベントを診断表示へ流す経路(guard event log の拡張か、別イベント種別か)の選定
  - 再読み込み時に起動時検証(Requirement 4-3)をどこまで再実行するかの整理
